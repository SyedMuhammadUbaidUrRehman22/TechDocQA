Implementation, step 1 (metrics and runner):

- **P1 metrics under Q-13 (P10-7, clarification).** The Q-13 text does not say how "count each item once" applies to precision and nDCG, or what a chunk holding two labeled items earns.
  - The rule: a result is *credited* when it holds a relevant item that no earlier result held.
  - **Precision@K** is credited results in the top K divided by K; missing results count as misses.
  - **nDCG@K** gives each credited result the gain 2^grade − 1 of the highest-graded item it newly finds, discounted by log2(rank + 1). The ideal ranks the labeled relevant items by grade, one per position.
  - Both stay between 0 and 1 for any ranking, and a repeat earns nothing, as in Recall@K.
  - A question with n labeled items scores at most n / K on precision.
  - In the stored baseline run, no smoke chunk holds two labeled items, so the rule changes no current number. The policy ID stays `q13-v1`.
- **Fingerprint scope.** `results_fingerprint` hashes only the P0 part of each configuration summary: an allowlist of the P0 keys, with only Recall@K and MRR. Precision@K, nDCG@K, latency and paired differences are derived from the fingerprinted ranks and labels, so leaving them out loses nothing and keeps the P0 baseline comparable. Checked on the real index on 2026-11-13: the smoke `eval` gave `48ce89dc...a3af410` at `a6f3bc8` before the change and again after it, with every P0 metric identical in both modes.
- **Paired differences (P10-6, parameters fixed before any hybrid result).** Policy `paired-bootstrap-percentile-v1`:
  - Per-question differences, candidate minus baseline, over the answerable questions evaluated in both configurations, computed from the per-question values stored in the report.
  - 10,000 resamples with replacement from Python's `random.Random(20261113)`, seeded afresh for each comparison.
  - The 95% interval drops 250 sorted means from each end, the 251st and the 9,750th of 10,000. "Above 0" means the lower bound is strictly greater than 0.
  - The p95 latency is nearest-rank: the ⌈0.95 n⌉-th smallest per-question search time, over every question in the run.
  - The rule's pairs are hybrid against vector and hybrid with reranking against hybrid. nDCG@5 decides; Recall@5 and MRR, and vector against BM25, are descriptive.
  - The rule is judged on the full benchmark only. On smoke, which also calibrates FR-18, the verdict is diagnostic.
- **Configurations.** `eval --mode` takes `bm25`, `vector`, `hybrid` and `hybrid+rerank`; the default stays `bm25` and `vector`.

Implementation, step 2 (hybrid search):

- **Fusion (P10-1).** `rrf-v1` sums w_r / (k + rank) over the retrievers that ranked a chunk, in a fixed order, with ties going to `chunk_id`.
  - Each retriever searches to max(top_k, `candidate_depth`) with the same filters.
  - New settings `rrf_bm25_weight` and `rrf_vector_weight` default to 1.0. They, `rrf_k` and the depth enter only hybrid's IDs; a test checks that the `bm25` and `vector` IDs do not move.
  - `bm25` mode still fetches `top_k`, even above the depth.
- **Hybrid results.** A fused result keeps each retriever's rank where it ranked the chunk, both raw scores, and both component relevances in a new `relevances` field.
  - A component relevance is computed for every fused chunk. BM25 uses the lexical index's own scale, where a chunk sharing no query word scores 0. Vector uses Chroma's score where it ranked the chunk, and the cosine of the stored vector otherwise. A test checks that the two agree to 1e-6.
  - `relevance` is null for hybrid, which has no single scale. In degraded hybrid it is the surviving mode's relevance.
- **Hybrid scale.** Hybrid's `scoring_config_id` hashes both component scales and the fusion settings, because the fusion decides which chunks the gate judges. Hybrid's `retrieval_config_id` also hashes the BM25 and vector thresholds that would judge a degraded search.
- **Degradation (P10-2).**
  - A retriever error at run time gives the other retriever's results, `degraded = true`, the error code as `degradation_reason`, and the new `failed_retriever`. A request or configuration error still raises.
  - Both retrievers failing raises `HYBRID_SEARCH_FAILED`, naming both codes.
  - In `ask`, a degraded search that finds nothing is `generation_error` with the failed retriever's code, retryable. The failed retriever might have found evidence, so this is not `no_evidence` (FR-18.4).
  - In `eval`, any degraded search fails the hybrid configuration with `SEARCH_DEGRADED`, so a run with the embedder down cannot pass as a hybrid measurement.
- **Gate (P10-3), parameters fixed before any live hybrid run.**
  - `[retrieval.sufficiency.hybrid]` names a gate: `vector` (G1), `bm25` (G2), `either` (G3) or `both` (G4). It holds a threshold table for each component the gate judges.
  - A component passes on the kept chunks' relevances with the usual `min_top_score`, `min_chunk_score` and `min_supporting_chunks`. A chunk without that component's relevance does not count.
  - For a proposal, each question's statistic per component is the best relevance among its top results, which is what `min_top_score` judges. G1 and G2 are chosen by `balanced-accuracy-midpoint-v1` on that component. G3 and G4 combine those two thresholds, and leave-one-out re-chooses both.
  - The margin is the smallest distance from a question's deciding relevance to its threshold: the best component under either, the worst under both. A question that cannot flip is left out of the margin.
  - The selection policy is `fewest-loo-errors-then-margin-then-order-v1`: fewest leave-one-out errors, then the largest raw margin, then the order G1 to G4.
  - Margins are compared raw, although vector relevance spans a narrower range than BM25's. The report says so; nothing is normalized after the fact.
  - Degraded hybrid is judged by the surviving mode's own section, shown as `thresholds_from`. Those are the Phase 8 thresholds: a degraded search's top results are exactly that mode's, at the same depth and order.

Implementation, step 3 (reranking interface, with no model yet):

- **Interface (FR-15, P10-5).** `retrieval/rerank.py` sends the query and the first `rerank_max_candidates` candidate texts to a `Reranker`.
  - Results follow descending reranker score, with ties keeping the input order, cut to `top_k`.
  - Candidates beyond the maximum are dropped from reranking, so a request for more than the maximum gets at most the maximum. The configuration now requires `top_k <= rerank_max_candidates`.
  - Reranking works on any mode, since FR-15 depends on FR-12 or FR-13. It is off by default and switched by `[retrieval] rerank` or per request: `--rerank` / `--no-rerank` on `search` and `ask`, and `eval --mode hybrid+rerank` for metrics, `--answers` and `--refusal`.
  - Tests mock the reranker. Until the dependency gate (step 5) installs a model, `build_reranker` reports `RERANKER_UNAVAILABLE`.
- **Results (FR-15.5).** Each reranked result keeps its source metadata, its earlier ranks, scores and relevances, and adds `rerank` to `scores` (raw), `ranks` and `relevances`. Its `relevance` becomes the reranker's 0-1 value under `cross-encoder-sigmoid-v1`, 1 / (1 + e^-score).
- **Failures (FR-15.4).**
  - Any exception while reranking keeps the unreranked order, cut to `top_k`, with `degraded = true` and its code in `rerank_failure`. A runtime exception's detail never reaches the response. Wrong-length or non-finite scores count as failures.
  - A missing reranker configuration is `RERANKER_NOT_CONFIGURED`, a configuration error, not a degradation.
  - `degradation_reason` is the retriever's code when a retriever also failed.
- **Scale and IDs (P10-4).**
  - `[retrieval.sufficiency.reranked]` holds the reranker's thresholds. Its `scoring_config_id` hashes the policy, the reranker identity (`[retrieval.reranker]`: model, revision, file hashes, truncation length), the candidate maximum and the base mode.
  - So thresholds calibrated on hybrid candidates go stale, with a warning, for a reranked `bm25` or `vector` request rather than judging it.
  - Only a reranked request's `retrieval_config_id` carries this identity, so the unreranked IDs do not move.
- **Which gate applies.** The reranker's thresholds when it ordered the results, including after a retriever failure, because a cross-encoder score depends only on the query and the chunk. When it failed, the gate below it applies: the hybrid gate, or the surviving mode's if a retriever also failed. The response names the scale in `thresholds_from`.
- **Evaluation.** `hybrid+rerank` records the reranker's raw scores and proposes a `[retrieval.sufficiency.reranked]` section from its own relevances. A reranker failure on any question fails the configuration with `SEARCH_DEGRADED`.
- **Checked on the real index (2026-11-13).**
  - The smoke `eval` still gives `48ce89dc...a3af410` with the same `bm25` and `vector` IDs and calibrations. `verify_index.py --compare` passed in both modes.
  - The stored-vector lookup was checked on two real queries. Over the 40 chunks vector search ranked, it matched Chroma's relevance to within 2.2e-7.
  - The 8 and 9 chunks in each query's hybrid top 20 that only BM25 ranked got lookup relevances below the lowest vector-ranked score, as an exact search implies. Until steps 2 and 3, the hybrid rows report `failed: MODE_NOT_AVAILABLE`. `--answers` and `--refusal` take a search mode, so they refuse `hybrid+rerank`; reranking there follows the configuration (P10-9).

Implementation, step 6 (runs). The protocol below was fixed before the full benchmark was first run:

- **Smoke proposals.** `eval_a4d00103eb5645a89f93cf78065aecf0` ran smoke in all four configurations, and the owner adopted both new sections (see the owner decisions above).
- **One full run.**
  - All four configurations run in one invocation on `benchmark_full.jsonl` (SHA-256 `15c3bcb2...e0b0162a`), with no trial run of any mode on that file first. A completed configuration is never rerun.
  - If a configuration fails (it then has no rows), all four are rerun together once, and both reports are kept.
  - Both Ollama models are loaded first, `/api/ps` and free memory are recorded before and after, and nothing else runs alongside.
- **Frozen tunables.** The thresholds, the hybrid gate, the RRF weights and `k`, the candidate count, `top_k`, the truncation rule and the 4 reranker threads do not change after the full results are seen. An in-domain negative passing a gate is a finding to report, not a reason to recalibrate.
- **Held-out view.** The runner now compares any dataset with `benchmark_smoke.jsonl` beside the manifest.
  - It records how many questions are held out, and says so in the notes.
  - On a dataset with held-out questions, it prints no configuration section: proposals computed there are descriptive, not for adoption.
  - From the full run's stored JSON, the write-up reports metrics over the 16 new answerable questions per configuration, and each gate's pass or refusal for the 4 in-domain negatives. The P10-6 rule is judged on all 36 answerable questions, as fixed.
- **Refusal with the model.** `eval --refusal` asks the smoke questions, as in Phase 8, in `hybrid` and `hybrid+rerank`. The in-domain negatives are judged at the gate from the full run's relevances; they are not sent to the chat model.
- **Degraded hybrid.** One `base_url` serves chat and embeddings, so a dead-provider profile would stop chat too. A scratch script instead fails only the embedding call, on smoke, and records the gate that applies (bm25's thresholds) and its verdicts. It is a scripted check, not a CLI run.

## Phase 8 contracts (2026-11-04)

These rules implement FR-18 and the FR-21 QA slice, and resolve Q-07 for the two P0 modes. Q-07 was approved as implemented on 2026-11-07, with its policy IDs unchanged ([approvals](#p0-approvals-2026-11-07)); they are recorded in every score, threshold and report, and a later amendment changes them. Evidence is in [Phase 8](PHASE_8_STATUS.md).

- **Q-07 score scales.** Each mode has its own 0-1 relevance, returned as `relevance` on every search result; raw scores stay in `scores`. Vector relevance is the FR-12 score, `(cosine + 1) / 2` (`cosine-distance-half-v1`). BM25 relevance is the raw score divided by the most that query could score, `(k1 + 1)` times the sum of its tokens' IDF, with a token the corpus lacks counted at the IDF of an unseen term, `log((N + 0.5) / 0.5)` (`bm25-query-max-v1`). The divisor is fixed per query, so the BM25 ranking is unchanged. Counting absent words is what keeps a question about Terraform from looking relevant on its few common words. A tiny corpus can give negative IDFs, so the value is clamped to 0-1. Hybrid and reranker scales are not defined; they are P1 and need their own calibration.
- **Thresholds per mode.** `[retrieval.sufficiency.bm25]` and `[retrieval.sufficiency.vector]` each hold `min_top_score`, `min_chunk_score`, `min_supporting_chunks`, `calibration_run_id` and `scoring_config_id`. The scoring ID hashes what fixes a relevance value: the mode plus the embedding profile and score policy, or `k1`, `b`, the tokenizer and the BM25 relevance policy. Thresholds apply only while it matches the active configuration. A mismatch gives the warning `SUFFICIENCY_CALIBRATION_STALE`, and a missing section gives `SUFFICIENCY_NOT_CALIBRATED`. Either way the mode answers ungated and says so, and no mode ever uses another mode's thresholds. Top-k and candidate depth are not part of the scale.
- **Visibility (AC-18.5).** `retrieval_config_id` now covers top-k, candidate depth, the score scale and the thresholds that apply, with their calibration run ID, so `search` and `ask` report the same ID. Each QA response also carries `sufficiency` (thresholds, calibration run, top relevance, supporting chunks, verdict) and `llm_called`. `config-check` reports each mode as `calibrated`, `stale` or `not_calibrated`. The query log adds both fields.
- **Gate placement (FR-18.1, FR-18.2).** The gate judges the chunks kept after context trimming, so a chunk dropped to fit the window cannot count. It runs before the chat model is built. A failure returns `no_evidence` / `LOW_RELEVANCE` with fixed wording, no evidence, `chunks_used = 0` and no chat request. Nothing retrieved is still `NO_MATCHING_DOCUMENTS` and is decided first. `CONTEXT_WINDOW_EXCEEDED` and provider failures stay `generation_error`. The FR-18.5 phrase rule is unchanged. FR-18.2's optional closest chunks are not returned; the top relevance is.
- **Calibration rule (`balanced-accuracy-midpoint-v1`).** Every `eval` run proposes thresholds per mode from the top-1 relevance of the evaluated answerable questions and all unanswerable ones, judged before trimming. The proposal is the midpoint between neighboring scores that maximizes balanced accuracy; ties go to the wider gap. When the groups separate, that is the middle of the gap between them. `min_chunk_score` equals `min_top_score` and `min_supporting_chunks` is 1, because 30 questions cannot calibrate a second, independent threshold. Leave-one-out errors are reported. A proposal changes nothing until a person copies its section into the configuration, and the run that proposed it becomes the calibration run. Calibration and assessment use the same questions, so the results are not from a holdout.
- **Adopted calibration.** Run `eval_c4ab1f1397fa469489137f611b74cdf7` on 2026-11-04: BM25 `min_top_score = 0.297285`, vector `0.858223`, both from fully separated groups.
- **Refusal check.** `eval --refusal [--mode M]` asks every smoke question through `answer_question()` within the evaluation scope. AC-18.1 counts unanswerable questions returned as `no_evidence` and AC-18.2 counts answerable ones returned as `answered`; each needs at least 10 and 20 questions. The report counts chat requests among gate refusals, which must be 0. Answerable questions with flagged labels are left out, as in the retrieval metrics.
- **Cold start (Phase 7 open item).** The FR-16.7 default of 60 s stays for `ask`. A cold `ask` measured 43.8 s in total, of which 23.4 s was generation including the load, within the deadline. `eval --answers`, `eval --refusal` and the live injection test first preload the chat model with Ollama's empty-prompt request at the same `num_ctx`, bounded at 300 s and timed separately, so a load cannot time out the first answer. An `ask` that still times out returns retryable `LLM_TIMEOUT`. Ollama's `keep_alive` is unchanged.
- **BM25 and the corpus.** BM25 IDF depends on the corpus. Calibration searches the 20-document evaluation scope, while `ask` searches every eligible document, including the private DDIA supplement. The scoring ID does not include the corpus, because that would invalidate the thresholds on every ingestion. After a material corpus change, run `eval` again and review the proposal.

These rules implement FR-16, FR-17 and the FR-23 prompt slice, and resolve the QA parts of Q-08 and Q-15. Q-07 is untouched: no score threshold is applied in any mode until Phase 8 calibrates one. Evidence is in [Phase 7](PHASE_7_STATUS.md).

- **Citations (FR-17).** A marker is `[C1]`, `[C1, C2]` or `[C1; C2]`. An unknown label is removed from the answer text and from the citations, with one `INVALID_CITATION_REMOVED` per distinct label. After generation, each cited chunk must still belong to an eligible version's current artifact; otherwise it is removed with `CITATION_SOURCE_INACTIVE`. `source` is the registry `source_key`, and `source_url` is the stored URL or null. An answer left empty after removals is `NO_VALID_CITATIONS` in both modes.

## Phase 5 contracts (2026-11-02)

These rules resolve the Phase 5 portions of Q-02, Q-03, Q-06, Q-08, Q-15 and Q-16, and take precedence over earlier wording. Evidence is in [Phase 5](PHASE_5_STATUS.md).

FAISS was not needed. Vectors are also stored in the registry because AC-12.7 requires a rebuild from stored data.

- **Embedding profile.** Provider, model and digest, dimension, normalization, metric and both task prefixes define `profile_id`, which names the collection. A digest mismatch is refused. Changing the model requires `chunk` and then `index`; `index` reports `STALE_CHUNKS` otherwise. - **Q-16.** Entity filters use `verified_entities`, seeded only by tests until P1. Absent memberships mean no results and no model call.
- **Q-15 deletion.** A shared vector or snapshot stays while another source uses it. `delete` keeps run counts and one `DOCUMENT_DELETED` event naming only the ID and reason, and removes the document's own history. It requires `--yes`.
- **Reactivation.** Re-ingesting withdrawn bytes or equivalent content reactivates that version as `chunked`, or `normalized` if it never had chunks. It needs `index` before vector search sees it, normally with no model call. A newer active version takes precedence, and reprocessing alone never reactivates. Withdrawing an original promotes its earliest duplicate, as a source change does.

## Implemented Phase 2 contracts (2026-10-21)

SQLite schema version 1 uses standard-library `sqlite3`, foreign keys, checked values, unique source keys and `(document_id, raw_hash)` uniqueness. Transactions cover each success and its attempt/event/counters; failures are recorded in a separate transaction after rollback. An application ID/schema version prevents overwriting an unrelated or newer database. SQLite writer contention produces retryable `REGISTRY_BUSY` after the configured connection wait (default 5 seconds).

Source identity is the compact JSON pair `[normalized_filename, logical_name_or_null]`. Metadata and filename normalization applies Unicode NFC; Windows filename identity follows `os.path.normcase`. The source binds to a private canonical location. An equal filename/logical name at another location returns `SOURCE_KEY_COLLISION`; supply a logical name to register it separately. Canonical paths enforce safety and location binding, rather than redefining source keys. In-root symlink aliases resolve to the same source. Moving a file to another location is an explicit collision, not an automatic new version.

`document_id` identifies the source. `version_id` reserves a stable **provisional byte-registration** identity. `raw_hash` is SHA-256 of the exact bytes read; `content_hash` is always null until Phase 3 normalization. `attempt_id` identifies each attempted input, and `run_id` groups attempts. Different byte hashes create linked provisional registrations, not finalized content versions. The latest registration pointer identifies the last successfully requested byte candidate; returning to a previously registered byte hash reuses that candidate. It does not implement version restore or change an active finalized version.

| Input / event | Implemented result |
|---|---|
| Same source, unchanged bytes | Reuse document/version IDs and original snapshot metadata, `deduplicated=true`, one `DUPLICATE_SKIPPED` event; run `skipped` increases. |
| Same source, changed bytes | Same document, new provisional version ID/raw hash and predecessor link, `CHANGED_BYTES_REGISTERED`; old registrations are not superseded based on raw bytes. |
| Different source, identical bytes | New document and registration, `duplicate_of` references a byte-identical document. This is a provisional byte match, not authoritative normalized deduplication. No indexing occurs. |
| Same filename in different directories | Explicit `SOURCE_KEY_COLLISION` unless disambiguated with a logical name. |
| Validation/transaction failure | Persist an attempt error; no partial document/registration writes. Retrying unchanged valid input is safe. |
| Later failure of a provisional registration | `registered -> failed`, timestamped failure event; other registrations are untouched. Retry reuses the failed byte candidate, `failed -> registered`, `RETRY_REGISTERED`. |
| Mixed batch | Commit successes individually; every expanded input has an outcome/index. Any failed input makes CLI exit 1. All failed -> `failed`; mixed -> `completed_with_errors`; all success/duplicates -> `completed`. |
| Interrupted process | An OS registration lock releases on exit. On the next registration, unresolved attempts in orphaned runs become retryable `RUN_INTERRUPTED`, counters/status finalize, and reruns reuse committed registrations. A live run's lock returns `REGISTRY_BUSY` and prevents orphan recovery. |

Processing status retains the source vocabulary. Phase 2 writes `registered` and `failed`; `finalized=false` and `is_active=false` are separate eligibility fields. Registration is not retrieval eligibility. No normalized version or searchable source is claimed active. Full extraction statuses and normalization finalization are later work.

Q-06 policy for Phase 3: a failure before a normalized change is established must not supersede an existing finalized version. Once normalization confirms changed content, the new finalized version becomes active and the old one is superseded in one registry transaction, as FR-05 requires. A subsequent indexing failure does not silently reactivate the old version; retrieval will require both active eligibility and indexed processing state. Normalized duplicates must map their provisional registration to the existing finalized version while preserving attempt history and creating no additional finalized version. These finalization operations are not implemented in Phase 2.

Registration retains title/technology/category/version label/language/source URL/license, byte format/size and PDF page count. Explicit title wins, otherwise filename; format titles/sections/pages are loader work. URL credentials, query strings and fragments are removed before persistence; known credential fields/environment secret values are masked in metadata and recorded failures. Private absolute paths support collision checking but are omitted from CLI records/errors. No file body is stored in SQLite. Phase 3 must read a verified snapshot or recheck the source's raw hash before loading mutable local files.

Default CLI output is JSON, also selectable with `--json` before or after the command. Batch outcomes use input indices (directory members sorted by casefolded filename then filename); paths are omitted. Fatal/argument errors are section 8.4 JSON on stderr. Exit codes: 0 success/help/version, 1 configuration/registration/registry failure or partial batch, 2 invalid CLI syntax. Directory expansion is one level; nested/empty directories have explicit outcomes. Missing configured directories are allowed at configuration time and never created as input roots; inaccessible/existing nondirectory roots make configuration fail safely.

PDF metadata preflight uses pinned `pypdf` in an isolated, time-bounded subprocess. It checks structure/encryption/page count without text extraction or PDF action execution. Text loading must still use LangChain in Phase 3; see [format/metadata preparation](LANGCHAIN_INGESTION_PLAN.md).

## Phase 3B normalization and finalization (2026-10-22)

The authoritative roadmap assigns extraction, normalization and versioning to Phase 3 and chunking to Phase 4. It had no separate Phase 3B entry. The requested 3B is the remaining Phase 3 work, including local framework loading; indexing and retrieval remain deferred. `ingest` keeps registration/extraction contracts and `process [version_ids ...]` performs offline processing (no IDs selects the latest byte registration of each source). Runs use the existing attempts/events/counters with `stage=normalization`; registration runs still report `stage=registration`. JSON fields/exit rules are retained; process adds manifest warnings using the existing convention.

Normalization policy `technical-text-v1`:

- Outside protected code, CRLF and CR become LF, Unicode is NFC, interior spaces/tabs collapse, trailing prose whitespace and outer blank lines are removed, and three or more blank lines collapse to two (three LF separators). Leading indentation, line/paragraph boundaries, Markdown lists/headings and two-space Markdown hard breaks remain meaningful. Punctuation, identifiers, operators, paths and case are unchanged. Metadata is copied; normalized heading paths and half-open character code offsets are recomputed.
- Q-10 precedence: fenced backtick/tilde blocks (including an unclosed fence), same-line backtick inline code, indented lines (four spaces or a tab), and Phase 3A's explicit HTML code spans remain verbatim, including their line endings, whitespace and Unicode form. This deliberately takes precedence over prose LF/NFC rules. No inferred code span is permitted to override explicit HTML boundaries. Unmarked code in PDF/prose cannot always be identified; there is no semantic code detector.
- For PDF only, remove standalone decimal page numbers (optionally `Page N`) outside protected code. With at least three pages, remove repeated first/last nonblank lines present on at least 50% of pages; require at least three unprotected nonblank lines on a page before nominating edges. Interior repeated body text is retained. This conservative edge heuristic is explicit; arbitrary/multi-line headers and layout reconstruction are not promised.
- Join alphabetic `prefix-` + LF + `suffix` only if the joined, case-sensitive word already occurs in that document's prose vocabulary (including other pages). Unknown compounds/hyphenation remain intact. There is no downloaded dictionary, language model, transliteration, punctuation stripping or case folding.
- Empty/insufficient content yields `NO_TEXT_EXTRACTED` (configured default 100 non-whitespace characters across pages). Invalid controls, replacement characters, lone surrogates or malformed/overlapping code offsets fail with `INVALID_EXTRACTED_CONTENT`. No LLM/provider is involved. The Unicode database version is recorded with the policy for reproducibility across Python versions.

Hashes remain distinct. `raw_hash` is SHA-256 of immutable source bytes (online: fetched HTML entity bytes); it is never changed by processing. Phase 3A `extracted_hash` remains the hash of its UTF-8 extracted text. `processing.extracted_hash` instead hashes the exact JSON artifact containing ordered original extracted Documents and their metadata, named explicitly by its `.json` path. Authoritative `content_hash` / `processing.normalized_hash` / `online.normalized_hash` is SHA-256 of normalized page texts in source order joined by exactly two LF characters, encoded as UTF-8 without BOM or an added terminal newline. Newlines already inside protected code are retained. Page/heading/citation metadata is stored separately in a hashed normalized Documents JSON artifact; metadata changes alone do not affect `content_hash`. This is not a chunk hash; no chunks or chunk identity are created.

Local loaders: LangChain TextLoader for UTF-8 Markdown/TXT, Latin-1 fallback for TXT only (record encoding); recover decoded raw newlines after TextLoader's universal-newline conversion so protected code remains exact. PyPDFLoader uses page mode with image extraction disabled, retains zero-based `page_index` and exposes one-based citation `page`. HTML reuses the Phase 3A local BSHTMLLoader adapter. Only allowlisted handle-validated local bytes matching the registered hash can first be captured; immutable private snapshots are used thereafter. Title precedence is explicit user > format title > filename; a new `title_explicit` JSON flag preserves intent. Legacy records without the flag infer filename fallback by equality; an old explicit title identical to the filename is inherently ambiguous.

Online processing verifies both saved raw and extracted hashes and normalizes the existing extracted text; it never fetches or re-extracts HTML. URL identity, actual response URL, publisher hostname, retrieval metadata, MIME/charset, title, documentation version if supplied, usage status, headings/code and original extraction provenance stay available. Missing documentation version/license is not guessed. Processing uses a separate terminating worker with the configured parse deadline and denied socket/DNS calls. Each processed artifact read is bounded to eight times the source-size limit (including JSON overhead). No body text is stored in SQLite; local raw files use `local/snapshots`, and extracted Documents JSON, normalized UTF-8 text and normalized Documents JSON use `processing/{extracted,normalized,documents}` under the ignored data directory. The existing content-addressed, fsynced, atomic hard-link publication is reused, with integrity checks before finalization and consumer reads.

Schema version 1, its application ID, tables, CHECK constraints, `(document_id,raw_hash)` uniqueness and partial unique active-version index are unchanged after inspection. Typed optional `processing` and `title_explicit` fields fit existing `metadata_json`; processing-run stage is derived from its existing run event. Existing Phase 2/3A records need no SQL migration; tests compare schema SQL before/after and reopen legacy-shaped rows. As with Phase 3A, older readers cannot read newly extended JSON and downgrades are unsupported.

| Processing decision | Persisted result |
|---|---|
| First normalized content for a source | Existing provisional ID is finalized, `status=normalized`, authoritative content hash assigned and `is_active=true`. |
| Changed source bytes, different normalized content | New byte candidate is finalized; previous active row becomes `superseded`/inactive in the same `BEGIN IMMEDIATE` transaction. |
| Changed bytes, same normalized content for that source | Keep the byte candidate/raw provenance/history but leave `finalized=false`, SQL `content_hash=null`, inactive and `status=normalized`; `processing.resolved_version_id` links to the existing finalized version. The process result returns the resolved version ID, `deduplicated=true`, `DUPLICATE_SKIPPED`. Candidate normalized hash/artifacts remain in processing metadata. No duplicate finalized content version. |
| Exact bytes or metadata-only repeat | Reuse byte ID and immutable first metadata; processing verifies stored artifacts, skips work and returns the resolved finalized version. Every request has an attempt. |
| Distinct source with equal normalized content | Finalize its own version/document and provenance; authoritative `duplicate_of` points to the earlier source still actively serving that content (see Review corrections). Future indexing must skip `duplicate_of` by default. Identity is never merged. |
| Return to historical bytes/content | Resolve the historical finalized version without reactivating it; preserve the currently active version. Version restore remains out of scope. |
| Stale unfinalized candidate | `STALE_CANDIDATE`; only the latest requested byte candidate can finalize. Existing finalized history can still be inspected/verified. |
| Extraction/normalization/storage/validation failure | Bound processing attempt fails; unfinished candidate becomes `extraction_failed` for extraction errors or `failed` otherwise. Existing finalized rows stay unchanged and active. Registration/fetch failures retain their prior behavior. |
| Interruption/contention | OS lock prevents competing runners; SQL transactions serialize finalization and recheck the latest candidate. On the next run, pending bound attempts get `RUN_INTERRUPTED` and their unfinished candidates fail; committed finalizations/outcomes survive. Retry reuses candidates/snapshots. SQL failure rolls back hash/eligibility/supersession/attempt/event/counters together. |

`documents.current_version_id`, `get_document` and `list` still mean latest requested byte registration, which can be a failed or duplicate candidate; it is not the active-version pointer. History/get_version expose finalized active and superseded records. `finalized_documents(resolved_version_id, settings, registry)` verifies artifacts and provides framework Documents with registry-owned IDs/provenance; future indexing must additionally require active eligibility and apply the duplicate policy. Normalized does not mean indexed or searchable.

Complete immutable files may remain unreferenced after failed/interrupted processing; no evidence is deleted automatically. Local failed processing can reuse the content-addressed raw snapshot even if the original input disappears. Before its first capture, changed/missing original bytes require re-registration. The online runtime manifest is regenerated after processing; export failure only warns/exits 1 and does not undo committed versions. Regeneration remains possible through the existing export API. Reference corpus selection/freeze is still separate.
